# Правила работы: сайт кодом через Claude Code

Этот файл – универсальный. Он не про проект, а про то, как мы работаем. Проектное состояние живёт в `docs/design-system.md`, решения – в `LOG.md`, бриф – в `brief/brief.md`. Дизайн собирается сразу в коде – Astro (HTML/CSS/JS в компонентах) – и смотрится в браузере: Figma в проекте нет.

## Файлы
- `brief/source/` – бриф клиента в любом формате. Читать целиком.
- `brief/brief.md` – бриф в едином формате. Заполняется из source в первом чате. Чего нет у клиента – в «Открытые вопросы», не выдумывать.
- `brief/references.md` – референсы словами: что берём (структура, ритм, плотность, настроение), не «сделай как здесь».
- `LOG.md` – журнал решений. Каждое продуктовое, процессное и технологическое решение из чата записывается туда в том же ходу, новые записи сверху. Начиная новую сессию – прочитать вместе с брифом.
- `docs/design-system.md` – источник правды о дизайне: токены, компоненты, карта секций, ручная доводка, журнал. Если расходится с кодом – прав код, базу поправить в том же ходу.
- `docs/TASTE.md` – как не сделать generic-дизайн. Читать перед концептами и перед каждой новой секцией.
- `docs/motion.md` – библиотека приёмов движения и реестр `data-reveal`. Новый приём – сначала сюда, потом в `src/lib/motion.js`.
- `docs/scene.md` – правила для 3D. Сцена появляется только если она фирменный приём, записанный в «Принятых решениях».
- `src/` – сам сайт на Astro. Движение – GSAP (ScrollTrigger, SplitText, CustomEase) + Lenis, 3D – Three.js, всё из npm, Astro собирает.
  - `src/pages/index.astro` – главная: секции подключаются в порядке карты, по строке на секцию.
  - `src/sections/<Имя>/` – секция, три файла: `<Имя>.astro` (разметка и тексты, один `<section id="…">`), `<Имя>.css` (стили), `<Имя>.js` (своё поведение, если есть). CSS подключается во frontmatter (`import './<Имя>.css';`), JS – в `<script>import './<Имя>.js';</script>`. Имя папки – PascalCase (`HeroIntro`), класс блока – kebab-case (`.hero-intro`).
  - `src/components/<Имя>/` – всё, что повторилось дважды, та же тройка файлов.
  - `src/layouts/Base.astro` – каркас страницы: `<head>`, шрифты, глобальные стили, запуск движения.
  - `src/styles/tokens.css` – единственное место сырых значений; `src/styles/base.css` – reset, сетка, шкала текста, состояния `data-reveal`. Оба глобальные.
  - `src/lib/` – общий JS: `gsap.js` (единственное место импорта и регистрации GSAP и плагинов), `env.js` (режимы `?static` / reduced-motion и `onMotion()`), `main.js` (запуск, Lenis), `motion.js` (реестр приёмов `data-reveal`), `scene.js` (Three.js, грузится лениво).
  - `src/assets/img/` – картинки (через `<Image>`); `public/video/`, `public/models/` – файлы как есть; источники всех – `src/assets/SOURCES.md`.
  - `src/pages/concepts/` – концепты и ветвления, `src/pages/dev/` – служебные страницы. В сборку для выкладки не попадают.
- Команды (`package.json`, Node 22.12+): `npm run dev` – просмотр на http://localhost:4321 (`.claude/launch.json`, конфигурация `site`), `npm run dev:stop` – остановить фоновый dev-сервер, `npm run build` – сборка в `dist/`, `npm run preview` – посмотреть сборку, `npm run check` – линтер правил, `npm run shot -- [id]` – скриншоты 1440 и 390 и замеры, `npm run versions` – что из библиотек устарело.
- `scripts/` – `check.mjs` и `shot.mjs`, только встроенные модули Node. Python и bash в проекте не используются.
- git – история проекта. Коммит после каждой закрытой секции и перед тем, как править поверх ручных изменений. «Что изменилось» – `git status` и `git diff`, а не по памяти.
- `.claude/skills/` – процессы: `section` (собрать секцию), `critique` (критика по TASTE), `check` (линтер и скриншоты), `motion` (новый приём), `scene` (3D в секции). `.claude/agents/` – `critic` и `qa` со свежим контекстом.

## Пайплайн
Работаем сразу в коде, но по воротам. Следующий этап не начинается, пока предыдущий не записан в `docs/design-system.md`.
1. Бриф → `brief.md` → «Контекст» и «Карта секций» в базе. Порядок секций = порядок аргумента. В карте у каждой секции: поверхность (светлая / тёмная), приём движения, есть ли 3D, адаптируется или стекается.
1a. Чтение брифа по TASTE.md: направление в одну фразу, три ручки, фирменный приём, чего не будет – записать в «Принятые решения» до первой строки разметки. Если фирменный приём – движение или 3D, это решается здесь, а не «добавим потом».
2. Hero: 2–3 направления отдельными страницами в `src/pages/concepts/` (`hero-a.astro`, `hero-b.astro`…, смотреть на `/concepts/hero-a`), каждая на `Base` и со своими токенами в `<style is:global>:root { … }</style>`. Не строить другие секции до выбора.
3. Выбор направления → токены зафиксированы в `src/styles/tokens.css` и в базе. С этого момента – никаких сырых значений вне `tokens.css`.
4. Сборка по одной секции за промпт (по просьбе – 2–3). Не трогать секции вне указанных. Процесс – скилл `section`.
5. Каждая секция закрывается критикой по TASTE.md (раздел 4), `npm run check`, `npm run shot -- <id>`, проходом по Definition of Done и коммитом.
6. Всё, что повторилось дважды, – компонент: папка `src/components/<Имя>/`, вариант – через проп и класс-модификатор (`.button--accent`), описан в базе.
7. Движение собирается вместе с секцией: каждому элементу – `data-reveal` с приёмом из `docs/motion.md`. Новый приём – сначала описать там, потом в `src/lib/motion.js`.
8. 3D – только там, где карта секций это предусматривает, по `docs/scene.md`. Не больше одной сцены на страницу без отдельного решения.
9. Адаптив – часть секции, не отдельный этап: скриншот 390 делается вместе со скриншотом 1440.
10. Публикация по `docs/publish.md`.

## Правила взаимодействия
1. Каждое решение дописывается в том же ходу: дизайн – в `design-system.md`, продукт, процесс и технологии – в `LOG.md`. Изменение, которое не записано, – не произошло.
2. Я правлю файлы руками между ходами. Перед правкой любой секции перечитай её и скажи, что изменилось (`git diff` с последнего коммита). Никогда не возвращай «свою» версию поверх моей.
3. Сначала критика – потом перестройка. Диагноз с селектором, строками файла и измеренными числами, а не «выравнивание выглядит странно».
4. Когда решение ветвится – 2–3 варианта отдельными страницами в `src/pages/concepts/`, рядом. Не спорь о хексах словами.
5. Похожее уже есть? Открой референсную секцию, прочитай реальные отступы, размеры и классы – и делай под стать. Не строй по памяти.
6. Текст из брифа не переписывать молча. Только предложение с пометкой «предлагаю заменить». Lorem ipsum запрещён – ни одного блока без реального текста.
7. Референсы описываем словами: что берём (структура, ритм, плотность), а не «сделай как здесь».
8. Возвращай список изменённых файлов и секций.
9. В конце каждой секции назови 2–3 места, где нужна ручная доводка. Результат не подаётся как финальный.
10. Библиотеки – из npm, точные версии (`.npmrc`: `save-exact`), последние стабильные (тег `latest`, без beta/dev): `npm run versions` показывает, что устарело; обновление – `npm install <пакет>@latest`, через мажор – только с чтением changelog и записью в `LOG.md`. Новая библиотека – одна фраза «зачем» и запись в `LOG.md`. Фреймворк – Astro, сайт собирается в статичные файлы. UI-фреймворки (React, Vue, Svelte), Tailwind и CSS-in-JS не приходят без отдельного решения в `LOG.md`.

## Жёсткие запреты (нарушение = переделка)

### Спейсеры
Пустые элементы-распорки запрещены. Расстояние между элементами – только через `gap`, `margin` и `padding` контейнера. Развести элементы по краям – `justify-content: space-between` или `flex: 1` у того, кто должен растягиваться. Перед отчётом найди все пустые `div`/`span` без содержимого и роли – их не должно быть. Декоративный пустой элемент (точка лейбла, линия) помечается `data-decor="что это"` и записывается в базе – иначе линтер считает его распоркой.
Исключение: таблицы и списки с цифрами – фиксированные колонки с выравниванием, иначе цифры пляшут по строкам.

### Хардкод цветов и размеров
Любой цвет, отступ, радиус, шрифт и easing вне `src/styles/tokens.css` – только через переменную; размер текста – только через класс шкалы. Перед созданием нового значения сначала ищи существующую переменную. Нужна новая – сначала добавь в `tokens.css` и в базу, потом применяй. Хекс или `px` отступа в CSS секции или компонента – ошибка. Каждый ход завершай `npm run check`: сырых значений в затронутых правилах = 0. Отчитывайся числом, а не словом «проверил».

### Лишние детали
Надзаголовки в капсе техническим шрифтом над заголовками, в углах карточек и над блоками – запрещены без исключений, с точкой-«диодом» или без. Подпись над заголовком – `title/xxs` основной гарнитурой в обычном регистре. Моноширинного шрифта и капса в проекте нет вообще, включая кнопки и чипы. Точка «·» как разделитель в строке – запрещена: разные сущности – разные чипы, одна сущность – обычный текст. Ничего, чего нет в задаче или брифе, не добавляется без одной фразы «зачем» в отчёте: бейджи, чипы, метки, приписки, счётчики, иконки-декор. Сомневаешься – убери. Подробно – TASTE.md.

### Позиционирование
Flex/grid вместо ручных координат. `position: absolute` и `transform` – только для декоративных элементов (наклон стикера, точка лейбла, холст сцены), и об этом пишется в базе.

### Масштаб текста
Не подгоняй размер текста числом «на глаз» – только классы шкалы; исключение – `clamp()` для одного H1, записанный в базе.

### Движение и 3D
Движение без приёма из `docs/motion.md` – ошибка: сначала описание, потом код. Пин-секция – не больше одной на страницу. Анимация на каждом элементе «потому что можно» – штамп, см. TASTE.md раздел 2. 3D-сцена без строки в «Принятых решениях» – убрать. Всё движение уважает `prefers-reduced-motion` и режим `?static`.

## Грабли (дописывать всё, на что наткнёмся)
- Всегда смотри, на каком фоне будет стоять элемент. Тёмные карточки на чёрном фоне – только приподнятая поверхность с обводкой или без, не чёрное на чёрном.
- Серый текст на тёмном – только светлый серый и крупнее 18 px; серый на светлом – только display-размеры.
- Белого текста на акценте не бывает, акцентного текста на светлом не бывает – если акцент светлый. Контраст проверяется числом.
- Скриншот после сборки обязателен, на 1440 и 390 (`npm run shot -- [id]`): смотри на результат глазами, а не по разметке. Длинная страница режется на куски по два экрана (`desktop-1440-2.png`…) – целиком такую картинку не прочитать. `scroll-behavior: smooth` ломает программный скролл при съёмке – в проекте его нет, скролл делает Lenis.
- Обложки 4:3 в карточках 4:5 режут содержимое – подбирать `object-position` или менять ассет.
- Headless-Chrome с `--window-size` уже ~500 px не сжимает окно, а режет скриншот: в `shot.mjs` мобильная ширина – эмуляция устройства через DevTools Protocol, не размер окна. `/dev/mobile` (iframe 390, `src/pages/dev/mobile.astro`) – только для ручного просмотра во встроенном браузере.
- Мобильный горизонтальный скролл `shot.mjs` ищет сам: элементы с `getBoundingClientRect().right > clientWidth` – виновники обычно отрицательные поля лент и строк списков в секциях без wrapper. `overflow-x: clip` у body прячет симптом, а не причину.
- Видео в проект – только через ffmpeg (`scale=640:-2`, `libx264 -crf 28 -preset slow`, `+faststart`) в `public/video/`, исходники не выкладываются; в разметке `data-src="/video/…"` + `preload="none"`, `src` подставляет `src/lib/main.js`, когда секция близко. Локальный сервер – HTTP/1.1, шесть соединений на хост: видео вне кадра не должны иметь `src`.
- Скриншот для проверки – `?static` (анимации выключены, всё видно) и `&to=<id>` для нужной секции: прокрутку headless не рисует, поэтому `to` сдвигает страницу отрицательным margin.
- GSAP-твин `rotation/scale` на inline-SVG внутри таймлайна с `clipPath` на родителе застревает в стартовом состоянии – для иконок использовать CSS-переход по классу.
- Маска SplitText при интерлиньяже ниже 1 режет выносные элементы букв – после появления маски снимаются (`split.revert()`).
- Встроенный браузер Claude, когда панель скрыта: rAF и тикер GSAP стоят, `setTimeout` дросселируется. Проверять логику через JS (`gsap.ticker.tick()` вручную, `gsap.getProperty`), статику – через `?static`, hover – на `?static&to=<id>` с реальным наведением.
- Правки стилей скриптом – только с проверкой, что якорная строка найдена (`throw`, если нет): `str.replace` по отсутствующей строке молча ничего не делает.
- GSAP не понимает строку `cubic-bezier(…)` в `ease` и молча ставит свой дефолт. Easing из токенов – по имени через CustomEase: `--ease-sharp` → `ease: 'ease-sharp'`, регистрирует `src/lib/motion.js`.
- `html.has-motion` ставится `<script is:inline>` в `<head>` (`src/layouts/Base.astro`) до первой отрисовки: если ставить его из `main.js`, контент сначала мелькнёт, потом спрячется под появление.
- CSS секций и компонентов (`<Имя>.css`) – глобальный, Astro его не изолирует. Поэтому каждое правило содержит класс своего блока: `.hero`, `.hero__title`, `.hero--dark`; чужие классы – только как контекст (`.section--dark .hero__title`). Без префикса стили протекают в другие секции – линтер это ловит.
- GSAP импортируется только из `src/lib/gsap.js`: прямой `import … from 'gsap'` в секции – вторая копия регистрации плагинов. Своё движение секции (`<Имя>.js`) – внутри `onMotion(() => { … })` из `src/lib/env.js`, иначе оно сработает в `?static` и при reduced-motion. Появление элементов – через `data-reveal`, а `<Имя>.js` – для того, чего нет в реестре: пин, scrub, hover, своя таймлиния (приём – сначала в `docs/motion.md`).
- В `src/pages/` нельзя класть `.js` и `.css` рядом со страницей: `.js` там Astro считает маршрутом. Поэтому концепты – один файл `.astro` со своими стилями в `<style is:global>`.
- HTML-комментарии `<!-- -->` в `.astro` попадают в готовый HTML. Пояснения – `{/* … */}` в разметке или комментарии во frontmatter.
- `public/` копируется на хостинг как есть: служебных файлов (источники, черновики) там быть не должно.
- Astro 7 в среде агента (Claude Code) сам уводит `astro dev` в фон: остановить – `npm run dev:stop`, статус – `npx astro dev status`. Искать и гасить процессы – только по PID своего проекта, не по общему шаблону: на машине бывают dev-серверы других проектов. `shot.mjs` поднимает свой экземпляр с `--ignore-lock` и гасит его группой процессов.
- Висячие строки: у текста стоит `text-wrap: balance` / `pretty`, но блоки с `<br>` Chrome не балансирует – там `&nbsp;` руками.
- Чередовать поверхности секций (светлая / тёмная) и брать сетки из референса: объясняющая секция с окном 10/12, лента 4/12, лево-правый паттерн, карточка на границе листа.
- Three.js: холст с `devicePixelRatio` без потолка кладёт ноутбук – в `scene.js` потолок 2. Сцена вне экрана рендерить не должна – `IntersectionObserver` ставит на паузу. Модели тяжелее 2 МБ – пережать (`gltf-transform`, Draco) до того, как класть в `public/models/`.

## Definition of Done секции
Секция не готова, пока не выполнено всё:
- flex/grid на всех уровнях, ширина по сетке 12 колонок на 1440 и по правилам ≤ 768 / ≤ 500;
- нет пустых элементов-распорок;
- все цвета, отступы, радиусы, шрифты – через переменные, все размеры текста – через классы шкалы, `npm run check` = 0 замечаний;
- нет скрытых блоков «на потом» и закомментированного кода;
- `id` секции совпадает с именем в «Карте секций», секция подключена в `src/pages/index.astro`;
- каждому появляющемуся элементу назначен `data-reveal` из `docs/motion.md`, при `?static` и `prefers-reduced-motion` всё видно;
- если в секции есть сцена – она ленивая, на паузе вне экрана, есть запасной вариант без WebGL;
- сделан скриншот на 1440 и 390 (`npm run shot -- <id>`), сверен с брифом; горизонтального скролла и ошибок консоли – 0, висячие строки разобраны;
- пройдены три вопроса критики из TASTE.md, штампы названы и оправданы или убраны;
- названы 2–3 места для ручной доводки, записаны в раздел «Ручная доводка»;
- изменение записано в журнал с именем секции и файлами;
- `npm run build` проходит без ошибок;
- секция закоммичена в git.
Отчёт «готово» без этого списка не принимается.

## Сборка и публикация
Сайт – Astro, собирается в статичные файлы: `npm run build` → `dist/`, на хостинге сервер не нужен. Правила с первого дня:
- только flex/grid, никаких абсолютных позиций и ручных координат вне декора;
- каждая секция – папка `src/sections/<Имя>/` (`.astro` + `.css` + `.js`) с одним `<section id="…">`, имя id как в карте; тексты – прямо в разметке секции (при переходе на CMS выносятся);
- стили секции и компонента – в его `<Имя>.css`, каждое правило с классом блока; `<style>` в секциях и компонентах не используется; глобальные – только `tokens.css` и `base.css`;
- шрифты из Google Fonts или самодостаточные файлы в `public/fonts/`; моноширинных и капса нет нигде;
- картинки – `<Image>` / `<Picture>` из `astro:assets`, исходники лучшего качества в `src/assets/img/`: WebP/AVIF, размеры, `srcset` и `loading` Astro ставит сам; `alt` обязателен (декор – `alt=""`), первый экран – `loading="eager"`; источник каждого – `src/assets/SOURCES.md`; видео – `public/video/`, модели – `public/models/`, их источники там же;
- брейкпоинты: 1440 и 390 (правила ≤ 768 и ≤ 500); продукт mobile-first – мобильный вид проектируется наравне с десктопным; для каждой секции в карте указано, адаптируется она или стекается;
- имена файлов сборки Astro хеширует сам, `?v=N` не нужен; на проде файлы руками не править. Хостинг и шаги – `docs/publish.md`.

Каждая сессия заканчивается обновлением `docs/design-system.md` и `LOG.md`.
